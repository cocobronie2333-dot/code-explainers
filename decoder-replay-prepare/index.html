prepare 为 decoder 尾段准备什么？

决定本步哪些 token 需要经过 decoder replay，准备紧凑布局、attention 元数据和执行上下文。普通 prefill 可以只保留末尾窗口；decode 和需要 prompt 分数的请求保留全部 query 行。

源码版本：76ea9d24f155afe032ad9ac6c98717f1f7334f36。下方实例是教学数据，流程块长度不代表耗时；未进行 NPU 性能或正确性实测。

沿实际调用链阅读

EngramModelState.prepare_attn 的实际调用位置见来源；它先准备普通 attention 元数据，再调用本函数。

EngramModelState.prepare_attn → DecoderReplayState.prepare
    清理 → 初始化 → 检查条件 → 生成 plan → DP 协调 → 发布 replay 状态
模型 forward 到 replay 边界
    → dsv41_decoder_replay_forward → AscendDecoderReplayLayers.__call__
    → gather hidden states → run_layers → scatter outputs

prepare 本身不接收 hidden states，也不调用 decoder 层；它的产物由随后模型 forward 中的 adapter 消费。

跟踪一批 token

A 是 decode（1 token），B/C 是 prefill（各 6 tokens）；B 默认请求 prompt logprobs。切换窗口或 B 的保留要求，查看行映射。

示例假设 DP=1、无 PCP、非 dummy、eager。原 batch 有效 token 为 13，原执行宽度假设为 16。无请求裁剪时保持原 padded 宽度；裁剪后本例执行宽度等于保留数。

prepare 的分支结果

DP（数据并行）通过 CPU group 的 all_reduce 共享两行信息：是否压缩，以及各 replica 的执行 token 数。dp_tokens 是每个 replica 的计数向量，不要求这些数相等。

PCP（prefill 上下文并行）先从全局请求尾窗口确定本 rank 实际拥有的 query 行。没有尾窗口 token 的 rank 也可能参与 padding 和通信。没有有效 PCP replay 计划时，禁止各 rank 各自截取本地尾部。启用 PCP replay 后，还要重建全局 compact batch、slot mappings 和 hidden restore 索引。

准备后，谁消费这些状态？

状态作用
layers.rows原 batch 中要选取的 token 行；后续 adapter 用 index_select 抽取状态，用 index_copy_ 回填有效输出。
offsets / dropped_before各请求在紧凑布局中的边界 / 截至边界累计丢弃的行数。
positions / slots / replay_start由 gather kernel 生成，保证位置、KV 写入位置和 replay 可见范围匹配新布局。seq_lens 仍保留原请求的序列长度。
metadata用紧凑 query 边界、原 seq_lens/block table、重排后的 slot/position 和 RoPE 重建 DSA attention 元数据。
num_actual_tokens / num_tokens有效 token 数 / 实际执行宽度（可能含 padding）；dummy 的有效数固定为 0。
layers.context_factory指向 forward_context。后续执行 decoder 时才进入上下文，切换 metadata、DP 计数、padding/MC2 mask 等；退出时恢复外层上下文与共享 MC2 mask。

首次初始化分配 slot buffer，创建非 circular KV group 中适用的 DSA metadata builders、准备 source RoPE，并 warmup gather kernel。初始化发生在 capture/profile 等提前退出之前。

若 adapter 配有 write_batch_kv，它会先为全部 token 写 cut layer 的共享 KV，再进入紧凑 replay 上下文。裁剪的是后续 query/状态计算布局，并不会在 prepare 中删除已有 KV cache。

这些内容会给 QSLI 使用吗？

会，后续层走 A5 packed-cache 且 uses_candidate_filter 的路径时会使用。普通非 index-source 层直接复用 shared.topk_indices，不会再次调用 QSLI。

prepare → _build_metadata → self.metadata
  → forward_context 设置 attn_metadata
  → AscendDSAV41Impl._get_layer_metadata
  → _select_sparse_indices(metadata.indexer.cache)
  → indexer.select_projected → run_a5_indexer → _qsli
  → quant_sparse_lightning_indexer_metadata
  → quant_sparse_lightning_indexer
数据来源QSLI 如何使用
紧凑 query_start_loc（offsets）成为 source_metadata.query_start_loc，传入 cu_seqlens_q；专用 metadata 算子和主 QSLI 算子均使用。
原请求 seq_lens 与 block tablebuilder 派生 cache_seq_lens/cmp_residual，传为 seqused_k/cmp_residual_k；block_table 供 QSLI 访问分页 K。C2 时长度除以 2 取整，余数作为 residual。
layers.rowsadapter 据此压缩 hidden states 和所需共享行 buffer，使后续 Q/weights、candidates、candidate_lengths 对齐同一 token 顺序。rows 本身不是 QSLI 参数。
紧凑 positions 与 RoPE间接用于 query RoPE；positions 也用于算子后 prepare_indexer_indices 的结果整理，并非直接传给原始 QSLI 算子。

区分两种 metadata：prepare 的 builder 可生成 source_metadata.qli_metadata。但 _qsli 会移除 common 中这个 metadata，再用 candidate_lengths、query 边界和 K 长度调用 quant_sparse_lightning_indexer_metadata，生成真正传给 QSLI 的专用 tensor。

candidates / candidate_lengths 的内容来自 candidate-source 层的 QLI 输出；prepare 不生成候选内容。需要沿用这些行 buffer 时，adapter 根据 rows 选择；若 replay 从会重算候选输出的 cut layer 开始，相应 buffer 由该层重新填充。K 数据来自既有 index cache，Q/weights 来自后续模型投影。

例如教学 batch 的 query 边界从 [0,1,7,13] 变为 [0,1,7,9]，QSLI 按 9 个保留 query 的布局工作，K 侧仍使用原序列长度派生的 cache 长度，并没有同步缩成 9 个 K。
