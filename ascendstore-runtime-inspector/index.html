get_num_new_matched_tokens

先查询外部 KV 池能覆盖到哪里，再扣除本地覆盖，返回可新增复用的 token 数和调度级异步标志。

Bulk 当前路线 · 本地覆盖之外，还能复用多少？

谁调用它

vLLM Scheduler.schedule：本地 prefix-cache 查询之后，经 AscendStoreConnector 调用池 Scheduler。

输入 / 读取状态

request；num_computed_tokens：本地已有覆盖。当前上游调用点会先把本地 sub-block 尾部向下对齐为 block_aligned_local。

函数内部做什么

  1. 清理该请求上次查询遗留的 LoadSpec，避免重查由 hit 变 miss 时继续使用旧加载计划。
  2. 查询外部连续有效覆盖；按 EAGLE 尾块重算、全命中保留最后一个 token、private group 对齐等规则调整可计入的覆盖量。
  3. 计算新增量 max(调整后池覆盖 − 本地覆盖, 0)。
  4. 保存 LoadSpec，分别记录本地覆盖、调整后池覆盖和原始外部覆盖，供分配后确认及 Worker 规划使用。

返回时保证了什么

(新增外部命中 token 数, load_async)。例如本地 32、外部总覆盖 96，在无额外策略调整时返回 64，而不是 96。

两条路径对照

BULK可由配置选择 load_async。为 True 时，核心先安排目的 block，再将该请求放入 WAITING_FOR_REMOTE_KVS；该请求不进入当轮正常 forward，等接收完成后再调度。普通 Bulk 没有新增外部覆盖时不建立加载计划。
LAYERWISELayerwise Scheduler 强制 load_async=False，避免使用跨 step 挂起的异步加载路径。Worker 内部仍可用后台线程预取和逐层等待。即使新增外部 token 为 0，原始命中仍可能保留为后续处理的 LoadSpec。

阅读时留意

查询成功只是命中判断，KV 字节此时还没有搬到本地。
返回值是超过本地覆盖的新增量，不是从请求起点计数的外部总覆盖。
load_async=False 描述调度合同，不代表后台拷贝、预取或 NPU 运行全部同步。
原始外部命中与最终允许跳过计算的覆盖可能不同；不要把 kvpool_store_skip_tokens 和 kvpool_cached_tokens 混为一谈。
