    阅读前先分清这四件事
    • block ID ≠ key ≠ GVA。block ID 定位本地 HBM，key 标识池内对象，GVA 是 Memcache 池内地址。
    • 分配 ≠ 复制 ≠ 发布。申请到空间并不意味着其他请求已经能命中。
    • Save 不自动释放 HBM。本地块仍由 KVCacheManager / BlockPool 管理；Load 也不会消费或删除池内副本。
    • load_async 与逐层并行是两件事。整块模式可切换同步 / 异步；逐层 Scheduler 固定 load_async=False，但内部仍用传输线程和层级事件。
    本页的代码与硬件边界
    • 四层 × 八个逻辑块是教学布局，不是模型层数、实际地址或性能测量。展示的 SDK 调用来自固定版本源文件。
    • 主图将池内驻留层抽象为 DRAM。是否跨机、具体传输协议、内部 staging 或 SSD 层级取决于部署和 SDK，图中不推断物理链路。
    • 范围限定为 AscendStoreConnector；不混入 P/D 点对点 Connector。逐层支持范围按当前文档为 Prefill 节点。
    • 单 group / 单 rank 用于解释顺序。混合 Attention、TP/PP/PCP、KVPP、MTP 和 HBM 层复用会增加布局、掩码和同步分支。
    
 
    初始化、SSD 和源码入口
    共同初始化：NPUWorker.initialize_from_config → ensure_kv_transfer_initialized → NPUModelRunner.initialize_kv_cache → ActiveKVConnector → register_kv_caches → backend.register_buffer。Memcache 初始化 DistributedObjectStore；Mooncake 初始化其 DistributedObjectStore 客户端。Scheduler 侧逐层查询使用元数据客户端。
    Memcache 的 batch_get_key_info(for_load=True) 分支会对 SDK 返回的 SSD-only 对象尝试普通 GET 回温，再刷新 GVA。Scheduler 当前逐层可读性检查要求有效 GVA；不能仅凭“key 存在”推断可以直接 batch_copy。Mooncake 的 SSD 行为由 SDK / 后端配置处理。本页不模拟 SSD。
